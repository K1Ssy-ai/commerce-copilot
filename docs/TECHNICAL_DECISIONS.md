# ADR-001 · 首版离线演示的技术方案

日期：2026-10-29。状态：**完成方案记录，待用户启动功能阶段后实施**。本文完成 D03，不代表应用、数据文件或演示入口已经存在。

## 要解决的问题

首个可运行版本需要可复现地验证[商品筛选与本人订单查询](DEMO_SCENARIOS.md)，覆盖预算边界、缺货、缺失客户身份和订单越权。先确认业务结果与权限边界，再考虑模型如何理解问题和编排任务。

当前项目仍是文档版本。本次不安装依赖、不复制参考源码、不调用模型或真实商店接口，也不提前实现 D04 之后的任务。

## 方案选择与替代方案

| 关注点 | 首版拟采用 | 理由 | 替代方案与重新评估条件 |
| --- | --- | --- | --- |
| 运行环境 | Python 3.12、标准库 | 与当前已有环境一致，首轮业务演示无需额外依赖 | 使用其他版本前，先验证对应运行与测试结果 |
| 交互入口 | 命令行参数与固定演示场景 | 输入可重复，便于区分参数错误与业务查询结果 | 有明确 Web 交互需求时再评估 FastAPI 与页面方案 |
| 查询路由 | 显式的商品查询、订单查询入口 | 将查询行为和权限规则独立验证 | 需要自然语言理解、跨任务状态或中断恢复时再评估模型与 LangGraph |
| 演示数据 | UTF-8 JSON 虚构记录，只读加载 | 便于审阅，并且不需要数据库服务 | 存在持久化、并发或事务需求后再评估 SQLite；规模增长时再评估其他存储 |
| 金额比较 | 带币种的十进制金额，拟用 `Decimal` | 保持预算边界和金额含义明确 | 数据层也可采用最小货币单位整数，但须先约定币种精度；首版不混用两种表示 |
| 业务验证 | `unittest` 离线测试 | 围绕真实业务边界建立可复现验证，不依赖外部 API | 出现额外测试需求时再评估第三方测试工具 |

标准库能力依据：[argparse 命令行参数解析](https://docs.python.org/3.12/library/argparse.html)、[json 编解码](https://docs.python.org/3.12/library/json.html)、[decimal 十进制计算](https://docs.python.org/3.12/library/decimal.html)、[unittest 测试框架](https://docs.python.org/3.12/library/unittest.html)。上述业务选型是本项目的设计判断，不是这些文档对电商架构的推荐。

## 实现后的离线运行流程

以下是拟定的运行方式，尚无可执行的应用启动命令；实际命令将在 D07 实现并验证后写入开发说明。

1. 在 Python 3.12 环境中，从本项目加载原创实现和虚构商品、订单记录，不依赖参考 Fork 的运行环境。
2. 用户选择商品或订单查询场景，由命令行解析结构化参数。首版不承诺理解任意自然语言；演示问题中的品类、预算和订单编号需明确传入对应查询入口。
3. 商品查询校验品类、币种和预算，再筛选有货商品；金额从十进制文本构造，不能先转为二进制浮点数再转换。
4. 订单查询接收应用绑定的演示客户上下文，然后同时按订单编号和客户归属过滤。演示身份由场景装配层固定提供，不能从聊天文本中直接替换。
5. 返回稳定的业务结果，再由展示层生成文字。无匹配、缺失身份、无法解释的状态按[业务术语表](GLOSSARY.md)处理。
6. 查询不保存状态变更，不生成订单、不预留库存、不提交售后申请。

演示装配层的固定客户上下文只用于本地虚构数据；它不能代替未来真实业务中的登录、会话验证或服务端授权。

## 拟定的模块边界

| 模块 | 职责 | 不承担的职责 |
| --- | --- | --- |
| 场景与 CLI 装配 | 读取参数、选择示例场景、提供虚构客户上下文 | 不提供生产认证，不执行自然语言中的身份变更 |
| 商品查询服务 | 校验查询条件、筛选商品、返回可展示字段 | 不生成无来源的商品属性或锁定库存 |
| 订单查询服务 | 校验客户上下文并限制订单归属 | 不绕过归属校验，也不将内部越权原因直接暴露给用户 |
| 只读数据适配层 | 加载约定的数据，提供记录读取能力 | 不写回 JSON，不连接真实商店 |
| 展示层 | 将明确的结果转换为用户可读回复 | 不自行推断支付、物流或退款事实 |

商品和订单数据的具体字段及示例文件留到 D04 定义。这里不锁定目录结构或接口签名，避免文档方案先于实际验证成为无法调整的约束。

## 暂缓项与后续进入条件

- **模型与多智能体编排**：业务只读接口及其边界验证通过后，再验证问题理解和路由是否确实需要模型；不把模型输出当作订单授权依据。
- **政策检索与向量数据库**：SCN-003 属于 Knowledge 阶段，待政策文件、版本和来源定位约定后再选检索方案。
- **Web、Docker 和部署**：先完成可运行的本地入口及复现文档，再讨论展示界面与部署。
- **真实 WooCommerce 接入**：待用户明确需求、来源许可和凭据管理方式后，另写接口及授权方案。
- **订单修改、售后与退款执行**：后续单独设计提案、确认、幂等和结果核对，不作为首版只读演示的一部分。

## 验证记录与验收门槛

本次实际执行的环境检查：

```powershell
python --version
python -c "import argparse, json, decimal, unittest; print('PASS: argparse, json, decimal, unittest import successfully')"
```

本机输出为 Python **3.12.5**，四个模块均成功导入。这只证明当前环境具备这些标准库模块，不表示商品、订单或编排功能已运行，也不代表任何应用测试通过。

后续实现的首版验收仍须覆盖：

- 预算等于商品价格时可匹配；币种不明时澄清，非法金额明确拒绝。
- 缺货与错误品类不进入结果；无匹配时不生成替代事实。
- 订单归属在业务层校验；缺失身份不能查询，越权与不存在使用统一回复。
- 未知状态不被改写为待发货或已发货；不凭物流单号推断签收。
- 演示及测试离线运行，不要求 API Key，查询前后示例数据保持不变。
